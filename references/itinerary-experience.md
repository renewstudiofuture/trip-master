# 行程组织与增量调整

参考圆周旅迹的公开产品说明，把“收集地点 → 组织路线 → 按天查看 → 局部调整”的思路用于攻略。这里是文字与文件工作流，不代表连接该App、拥有其接口或实现实时多人同步。

## 输入先整理为候选

用户给攻略链接、文字或截图时先提取：地点、所属城市／分店、建议停留时间、推荐理由和原始来源。链接通过公开搜索／原文读取；截图通过现有图像能力读取。页面无法访问时说明缺失，不要求用户登录另一个平台。

同名或别名合并时核对位置，不能把不同城市、不同分店合并。分为“用户必去”“可以考虑”“暂不安排”；别人攻略中的时间、价格、开放情况必须重新核实，不能继承为事实。

## 先有日程，再补细节

每日卡片／表格包含：日期、当天重点、起终点、按顺序排列的地点、交通方式与时间依据、餐饮区域、当晚住宿、预约与行李事项。固定订单标“已锁定”，可移动活动标“建议”，雨天或体力不足时的替代标“备选”。

连住酒店在住宿汇总只核一次，每日注明回到该酒店即可。先按地理邻近和已定时间排序，再核关键交通；不为每个点补一个不可靠的分钟数。

附近探索只在确有空闲且用户愿意时加入一至两个可选点，不安排会赶不上车或挤占已订场次的绕路。公开来源没有可靠店名时保留区域建议，不造“隐藏宝藏店”。

## 局部修改，不重做整趟

用户说“明天下雨”“删掉这个点”“晚一点出发”时：

1. 找到受影响日期与固定订单。
2. 调整可移动活动，核对相邻交通、闭馆和预约冲突。
3. 明示哪些时间、预算或预订需要变化，固定订单不能自动顺延。
4. 更新同一份状态与攻略，不重新搜索无关酒店和景点。

多位同行者意见可以整理进同一份待决定事项表；发生冲突时询问真正影响安排的选择，不声称已得到未发言同伴的同意。用户需要分享时提供不含个人订单标识的文件；不得自动邀请、发送或发布。

## 地图与App边界

有可靠地点坐标时可生成按天点位图；没有坐标则提供地点顺序与可核实的导航入口。须区分坐标系，不画虚假的精确道路。多人出行不自动触发额外地图开发。

用户明确要将行程导入圆周旅迹时，先核实其当前实际支持的导入格式与可用工具，再操作或给适配文本。不能声称本包JSON／Markdown可直接导入该App，也不能自行创建账户、调用未公开接口或同步私密订单。
